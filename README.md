# Posts CRUD with Laravel MVC

This Laravel 10 project lets you create, read, update, and delete posts. Each post has a `title` and a `body`. This README walks through setup, the commands used to build the project, and how Model–View–Controller (MVC) works here.

## 1. Requirements

- PHP 8.1 or newer, with Laravel's required extensions
- Composer
- MySQL and an empty database for this project
- Node.js and npm for the Breeze authentication pages

The Posts pages use plain HTML, but the Breeze login, registration, and dashboard pages use assets built with Vite.

## 2. Run an existing copy

From this project directory, install dependencies and create a local environment file:

```bash
composer install
cp .env.example .env
php artisan key:generate
```

Create an empty MySQL database, for example `posts_demo`. One way to do this, if your MySQL user has permission to create databases, is:

```bash
mysql -u your_local_db_user -p -e "CREATE DATABASE posts_demo;"
```

MySQL will ask for that user's password. If you already created a database, use its name instead. Edit **your local `.env`** to point to it. These are sample values only; use your own local database credentials:

```dotenv
APP_NAME="Posts Demo"
APP_ENV=local
APP_DEBUG=true
APP_URL=http://127.0.0.1:8000

DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=posts_demo
DB_USERNAME=your_local_db_user
DB_PASSWORD=your_local_db_password
```

Keep the `APP_KEY` generated by `php artisan key:generate`. Do not commit your `.env` or put real passwords in this README. `.env.example` is a template.

Install and build the frontend assets, create the tables, and start the server:

```bash
npm ci
npm run build
php artisan migrate
php artisan serve
```

Open **http://127.0.0.1:8000/posts** for posts, or **http://127.0.0.1:8000/register** to create an account. The `/` route still shows Laravel's default welcome page.

## 3. Create the Posts MVC feature step by step

The command used to generate its starting files was:

```bash
php artisan make:model Post -mcr
```

`Post` is the model name. `-m` makes a migration, `-c` makes a controller, and `-r` gives the controller resource method stubs. Those generated files were then edited to add the post fields and CRUD behavior. The command was **already run** in this repository; run it when building a new project from scratch, not when setting up this copy.

| File | Role |
| --- | --- |
| `app/Models/Post.php` | Model: reads and writes `posts` rows |
| `database/migrations/2026_11_18_050803_create_posts_table.php` | Migration: defines the table |
| `app/Http/Controllers/PostController.php` | Controller: handles requests |
| `routes/web.php` | Routes: connect URLs to controller methods |
| `resources/views/posts/*.blade.php` | Views: show forms and posts |

### Step A: Define the table

The migration's `up()` method creates the table:

```php
Schema::create('posts', function (Blueprint $table) {
    $table->id();
    $table->string('title');
    $table->text('body');
    $table->timestamps();
});
```

Its `down()` method runs `Schema::dropIfExists('posts')` when rolled back. Apply a new migration with `php artisan migrate`.

### Step B: Set up the model

The model permits the form fields to be passed to `Post::create()` and `$post->update()`:

```php
class Post extends Model
{
    use HasFactory;

    protected $fillable = ['title', 'body'];
}
```

### Step C: Register the routes

In `routes/web.php`:

```php
use App\Http\Controllers\PostController;

Route::resource('posts', PostController::class);
```

| Action | Request | Controller method |
| --- | --- | --- |
| List posts | `GET /posts` | `index` |
| Open create form | `GET /posts/create` | `create` |
| Save new post | `POST /posts` | `store` |
| Open edit form | `GET /posts/{post}/edit` | `edit` |
| Save changes | `PUT /posts/{post}` | `update` |
| Delete post | `DELETE /posts/{post}` | `destroy` |

The resource route also registers `GET /posts/{post}` for `show`, but this project's `show()` method is empty. Read posts on the list page. To inspect the registered routes, run `php artisan route:list --path=posts`.

### Step D: Handle requests in the controller

`index()` gets posts through the model and sends them to the list view:

```php
public function index()
{
    $posts = Post::all();

    return view('posts.index', compact('posts'));
}
```

`create()` returns `view('posts.create')`. The form submits to `store()`, which validates the request and saves a post:

```php
public function store(Request $request)
{
    $validated = $request->validate([
        'title' => 'required',
        'body' => 'required',
    ]);

    Post::create($validated);

    return redirect()->route('posts.index');
}
```

This snippet omits the success message attached by the actual controller. `edit()` loads a post and shows the edit view. The update and delete actions work like this:

```php
public function update(Request $request, $id)
{
    $validated = $request->validate([
        'title' => 'required',
        'body' => 'required',
    ]);

    $post = Post::findOrFail($id);
    $post->update($validated);

    return redirect()->route('posts.index');
}

public function destroy($id)
{
    $post = Post::findOrFail($id);
    $post->delete();

    return redirect()->route('posts.index');
}
```

These simplified examples omit the success messages in the real controller. `Post::findOrFail($id)` returns a 404 response if the post does not exist.

### Step E: Make the views

`resources/views/posts/index.blade.php` loops over the posts passed in by `index()`:

```blade
@foreach ($posts as $post)
    <h2>{{ $post->title }}</h2>
    <p>{{ $post->body }}</p>
    <a href="{{ route('posts.edit', $post->id) }}">Edit</a>
@endforeach
```

The create view sends a POST request to the named `posts.store` route:

```blade
<form action="{{ route('posts.store') }}" method="POST">
    @csrf
    <input type="text" name="title" value="{{ old('title') }}">
    <textarea name="body">{{ old('body') }}</textarea>
    <button type="submit">Save</button>
</form>
```

`@csrf` supplies the security token Laravel requires for POST forms. `old()` restores input if validation fails; the existing view also displays validation errors. `resources/views/posts/edit.blade.php` uses `@method('PUT')` for updates, and the delete form in the list view uses `@method('DELETE')`. HTML forms use POST with these directives because they cannot send PUT or DELETE directly.

For example, the edit form submits to the named `posts.update` route:

```blade
<form action="{{ route('posts.update', $post->id) }}" method="POST">
    @csrf
    @method('PUT')
    <input type="text" name="title" value="{{ old('title', $post->title) }}">
    <textarea name="body">{{ old('body', $post->body) }}</textarea>
    <button type="submit">Save</button>
</form>
```

The list view's delete form similarly posts to `route('posts.destroy', $post->id)` with `@csrf` and `@method('DELETE')`.

## 4. How a request moves through MVC

1. Open `/posts/create`. The route calls `PostController::create()`, which returns the create **view**.
2. Enter a title and body, then press Save. The form sends `POST /posts` with a CSRF token.
3. The route calls `PostController::store()`. The **controller** validates the input.
4. `Post::create($validated)` uses the **model** to insert a row in the `posts` database table.
5. The controller redirects to `/posts`. `index()` reads the rows and passes them to the list view.

Editing and deleting follow the same pattern: route, controller, model, then a view or redirect.

## 5. Migration commands used while building the project

Only `php artisan migrate` is needed for normal setup. Rollback and refresh change the schema and can remove post data.

```bash
# Apply pending migrations.
php artisan migrate

# Reverse the latest migration batch.
php artisan migrate:rollback

# Reapply pending migrations after rollback.
php artisan migrate

# Reverse the posts migration by its exact file path.
php artisan migrate:rollback --path=database/migrations/2026_11_18_050803_create_posts_table.php

# Apply that migration by its exact file path.
php artisan migrate --path=database/migrations/2026_11_18_050803_create_posts_table.php

# Roll back all migrations, then run the available ones again.
php artisan migrate:refresh
```

`migrate:rollback` normally reverses the latest **batch**, which may include more than the posts migration. The path commands use this repository's migration filename; a newly generated migration will have a different timestamp. To inspect the migration state, run `php artisan migrate:status`.

In the example output, `migrate:refresh` said `Migration not found` for `2026_11_17_082710_create_students_table`. That means the database recorded an older migration whose file is no longer available. It is separate from the posts migration. Check the database migration history and restore the file if that older migration is still needed.

## 6. Authentication with Laravel Breeze

Breeze has already been installed in this repository with the **Blade with Alpine** stack. It provides registration, login, logout, password reset, password confirmation, profile editing, and a dashboard. This section records how it was added; **do not rerun the installer to set up an existing copy**. Use the setup commands in section 2 instead.

To add the same authentication scaffolding to a separate Laravel 10 project, run these commands from that project's directory:

```bash
composer require laravel/breeze --dev
php artisan breeze:install
php artisan migrate
```

When prompted by `breeze:install`, choose **Blade with Alpine**. This project's installer run also chose **No** for dark mode and **PHPUnit** for tests. The installer installed Node packages and built the assets in the pasted output. If you need to install or rebuild them yourself, run:

```bash
npm install
npm run build
```

The correct Artisan command is `php artisan breeze:install` (with a colon). The pasted attempts using `php artisan install breeze`, `php artisan breeze install`, and `php artisan install:breeze` did not install Breeze. The Composer option is `--dev` (two hyphens), as in the successful command above.

After starting the app with `php artisan serve`, you can visit:

| Page | URL | What it does |
| --- | --- | --- |
| Register | `/register` | Create an account |
| Login | `/login` | Sign in |
| Forgot password | `/forgot-password` | Request a reset link by email |
| Dashboard | `/dashboard` | View the signed-in dashboard |
| Profile | `/profile` | Edit account details and password |

Logout is a POST action in the signed-in navigation, not a page to open with GET. `routes/auth.php` defines the authentication routes. `routes/web.php` protects `/dashboard` with `auth` and `verified`, and `/profile` with `auth`.

Password reset emails require a working mail setup. For a local learning setup, you can add this **sample** value to your own `.env` to write outgoing mail to `storage/logs/laravel.log`, where you can copy the reset link:

```dotenv
MAIL_MAILER=log
```

This project still leaves `/posts` and its create, edit, and delete routes public. Breeze adds accounts and auth pages, but does not automatically restrict the Posts CRUD routes. Also, `app/Models/User.php` does not implement `MustVerifyEmail`, so the `verified` middleware on `/dashboard` does not currently require email verification. To require verification, the User model and mail delivery must be configured for it.
